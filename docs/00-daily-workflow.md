# 日常制作与发布流程

本文是 `项目说明.md` 的执行版，供 AI 在新对话中核对步骤。用户不需要手动执行命令。

## 一、本地制作

1. 阅读根目录 `AGENTS.md`、`项目说明.md` 和目标测试的 `项目说明.md`。
2. 新测试先建立独立目录、`test.manifest.json` 和项目说明。
3. 在测试目录内完成题目、选项、算法、结果、页面和素材。
4. 接入共享兑换码授权，不复制后台或服务器。
5. 运行测试包校验、类型检查、平台构建和自动测试。
6. 启动本地服务，用浏览器检查电脑和手机尺寸。
7. 把本地地址交给用户体验，根据反馈继续修改。

本阶段不得推送 GitHub、构建生产镜像或修改 Sealos。

## 二、用户验收

只有下面这种明确表达才进入发布阶段：

> 本地验收通过，可以上传并正式开放。

如果用户仍在询问、比较或要求调整，继续留在本地阶段。

## 三、正式发布

1. 再跑一次完整自动检查。
2. 检查源代码和构建产物中没有密码、密钥、明文兑换码或本地数据库。
3. 形成一次说明清楚的 Git 提交并推送 GitHub。
4. GitHub Actions 在 Linux 上依次执行校验和测试，构建以完整提交 SHA 命名的 Docker 镜像并推送 GHCR。
5. AI 运行 `npm run release:production -- --approval "正式开放"`。脚本会确认当前提交已经位于 `origin/main`，触发生产发布并等待结果。
6. 生产工作流先创建并核验 SQLite 备份，再使用受限身份更新 Sealos 的唯一应用。
7. 新实例就绪后，工作流检查全部入口和静态资源，并在 390px 手机浏览器中输入系统专用码、改选上一题、完成超级 SBTI 16 题并看到结果页。
8. 工作流解绑专用码，确认旧令牌失效、兑换门重新出现，然后才判定发布成功。
9. AI 记录提交 SHA、镜像、备份和 GitHub Actions 运行地址；这次纯文档提交不会重复构建镜像。

用户不需要保管命令，也不需要进入 Sealos。以后仍然只需在本地满意后说：`本地验收通过，可以上传并正式开放。`

## 四、失败处理

- 本地普通构建失败：修正后重新测试，不进入发布。
- 本机 Docker 不可用：按 `04-windows-docker-recovery.md` 识别已知故障；不让本机 Docker 长时间阻塞发布。
- GitHub 镜像构建失败：保留旧生产镜像，不更新 Sealos。
- 固定 SHA 镜像 5 分钟内仍不可用：终止发布，保留旧生产镜像并检查镜像工作流。
- Sealos 新镜像 3 分钟内未就绪，或公网浏览器验收失败：工作流自动切回上一镜像并再次等待就绪；除非数据库迁移不兼容，否则不恢复数据库。
- 整次工作流 15 分钟仍未结束：停止等待并根据 GitHub Actions 中最后一个步骤处理，不无限重试。
- 本机到 GitHub 的普通 Git 通道连接重置：最多再用 HTTP/1.1 重试一次；仍失败时使用项目内 GitHub API 备用脚本。它只在远端父提交未变化且上传 tree 与本地完全相同时更新 `main`。
